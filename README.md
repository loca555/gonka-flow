# Gonka Flow

## Публикация и новый интерфейс

- «Торговля» — отдельная вкладка с пулами, совмещённым графиком и сделками всех адресов. «Мост» — отдельная вкладка с чеканкой/сжиганием и ритмом чеканки. Лимита по объёму нет.
- Начальная вкладка — «Торговля» (#trading). #bridge открывает «Мост», прежний #mints перенаправляется туда же. Постоянный блок «Пулы и сделки WGNK» и строка снимка в торговле удалены; сообщения об ошибках сохранены.
- Кнопки «Найти продажи» / «Найти покупки» переключают сторону обмена; видимый статус показывает адрес и число исполнений.
- «Минтеры» — отдельная вкладка с балансами, датами первой/последней чеканки и продажами. Клик по адресу открывает диалог с балансом на проверенном блоке и всеми подтверждёнными покупками/продажами одним прокручиваемым списком, без страниц. Размер окна ограничен; сортировка всей истории и сохранение прокрутки при обновлении поддерживаются.
- Все 28 информационных столбцов четырёх таблиц сортируются кликом в обе стороны. Мост и сделки сортируются на сервере до пагинации; цены сравниваются точно, без float.
- Числа отображаются без дробной части, с пробелами между разрядами; ненулевые значения меньше единицы — «< 1». Цены в интерфейсе явно подписаны как USDT за 1 000 WGNK; API сохраняет USDT за 1 WGNK и точные суммы. Комиссии пулов указаны целыми базисными пунктами.
- Общий график торговли: синяя линия цены, составные дневные столбцы объёма — зелёные покупки + красные продажи. В режиме «Все сделки» карточки отдельно показывают WGNK, USDT и среднюю цену каждой стороны. Дневная подсказка разделяет объёмы, суммы USDT и число исполнений. Часовой пояс Asia/Nicosia сохранён, географическая подпись не выводится.
- /api/mints/address/{address} возвращает всю подтверждённую историю адреса и address_balance на едином snapshot. Баланс восстановлен из сверенной истории чеканки, сжиганий и переводов; он не равен покупкам минус продажам и не заменяется нулём при ошибке. Дневные агрегаты API содержат bought_raw/sold_raw, buy_quote_raw/sale_quote_raw и buys_count/sales_count до пагинации.
- LIVE и покрытие — компактно в правом верхнем углу; прежняя панель фильтров чеканки удалена.

### Бесплатный Render

`render.yaml` задаёт только один Free web service, без диска, платного cron и отдельных БД.
При `LOAD_SEED_ARCHIVE=true` пустая среда восстанавливает проверяемый архив из `app/seed-data`, затем догружает Ethereum.
Архив содержит только финальные публичные WGNK-события, реальные интервалы покрытия и сверенный снимок. GNK, labels, локальные ключи, RPC-конфигурация и пользовательские исследования исключены.
Существующая runtime-база никогда не заменяется архивом. Локальный Docker по умолчанию не включает восстановление.

Ограничения Free: сон после 15 минут простоя, потеря новых локальных данных при рестарте/деплое/сне, 750 часов на весь workspace и квоты трафика/сборок. HTTP-пинг не обеспечивает сохранность SQLite. Это бесплатный preview, не гарантия работы 24/7.
Документация: https://render.com/docs/free

Обновление архива: `python -m app.seed export /path/to/gonka-flow.sqlite3 app/seed-data`.
Источник открывается только для чтения. Экспорт проверяет покрытие, предложение и балансы пулов; манифест содержит SHA-256. Публикуйте новый архив вместе с проверенной версией кода.
Проверки: `python -m unittest discover -s tests -q` и `node tools/dashboard-check.cjs`. Прежние три UI-entrypoint вызывают тот же актуальный набор проверок.

Локальный монитор чеканки и рынка WGNK в Ethereum. Без подключения кошелька, ключей, подписания и отправки транзакций.

**Локальная панель: http://127.0.0.1:8790**

## Текущий режим: WGNK на Ethereum

Docker запускается с **APP_MODE=mints**. Работают три Ethereum-задачи: новые WGNKMinted, история чеканки и анализ переводов/сделок двух проверенных пулов Uniswap V3 WGNK/USDT. GNK, майнинг, перепись держателей, внешние ценовые сервисы и проверка обратного моста в Gonka не запускаются. Старые API полного режима по-прежнему отключены (HTTP 410). Ранее накопленные данные не удаляются.

- История от фактического блока создания контракта WGNK, а не от 7 июня. Граница проверяется по коду контракта в соседних Ethereum-блоках.
- В интерфейсе minimum=0: выпуски и сжигания любого размера. API сохраняет фильтры для программного использования.
- Даты и дневные агрегаты в Asia/Nicosia с летним/зимним временем. Unix ts остаётся UTC, CSV дополнительно содержит time_local с явным смещением. Точные суммы, получатели, Request ID, эпоха, финальность и ссылки на Etherscan.
- Фильтры периода и адреса/хеша остаются у торговли; сортировка, пагинация, светлая/тёмная темы.
- Ритм чеканки — интерактивный график / столбцы. Торговый график совмещает дневной объём столбцами и взвешенную цену линией.
- Распределение эмиссии: WGNK в двух отслеживаемых пулах, вне них и сожжённые на Ethereum. Все части относятся к одному финальному блоку; totalSupply и balances пулов сверяются через eth_call с полной историей.
- Продажи — валовой объём исполнений Swap, не количество уникальных токенов; могут повторяться и пересекаться с остатками в пулах. Цена = выход USDT / вход WGNK в пул, округление вниз до 12 знаков; газ и дополнительные комиссии маршрутизаторов не учтены.
- «Торговля» по умолчанию объединяет покупки и продажи. Отчёт по минтерам показывает балансы и продажи с подтверждённым оттоком WGNK у инициатора receipt. Это сопоставление адресов, не отслеживание индивидуальных монет. Обычные переводы не считаются продажами.
- CSV рядом с «Лента мост» выгружает и чеканку, и сжигания без порога, с точными суммами. Старый CSV чеканки сохраняется в API.
- Полнота считается по непрерывному покрытию блоков от создания контракта до известного финального блока. При ошибке RPC диапазон и курсор не продвигаются.
- Проверенные финальные диапазоны старого Ethereum-архива переиспользуются, источник каждой записи сохраняется. Для новых выпусков дополнительно сверяются receipt и ERC-20 Transfer от нулевого адреса. Предварительные события перепроверяются и не входят в итоги по умолчанию.

Чеканка **не означает покупку**. Получено при чеканке — не текущий баланс адреса, сумма выпусков — не текущая эмиссия после сжиганий. Сторона GNK и блокировка средств сейчас не проверяются. Данные зависят от Ethereum RPC, это не собственный full node.

API: [описание](http://127.0.0.1:8790/api/docs), /api/mints, /api/mints/bridge, /api/mints/bridge/export.csv, /api/mints/tx/{hash}, /api/mints/export.csv, /api/mints/flows. Мост обновляется каждые 15 с, рынок — 20 с, открытый диалог адреса — 30 с; сбор не зависит от вкладки. Для остановки сборщиков задайте INDEXER_ENABLED=false и пересоздайте контейнер.

## Возможности сохранённого режима full (сейчас выключены)

- Поток денежных событий Gonka и WGNK: адреса, точные суммы, блоки, транзакции, типы операций и исходные доказательства.
- Покупки/продажи в двух проверенных пулах Uniswap V3 WGNK/USDT; рейтинги инициаторов с подтверждённым направлением WGNK в receipt.
- Раздельный учёт переводов, swaps, ликвидности, залога, выплат и вестинга.
- GNK → WGNK: сопоставление блокировки и выпуска по keccak256(request ID), сумме и Ethereum-получателю.
- WGNK → GNK: сжигание и проверка завершённой записи Gonka по Ethereum-блоку, индексу receipt, контракту и сумме.
- Активные хосты текущей эпохи: адрес, заявленный endpoint, модели, вес PoC и концентрация.
- Поиск кошелька: текущий GNK / WGNK баланс, локальная история, связанные маршруты моста.
- Держатели GNK и WGNK: сортировка по точному балансу, порог по умолчанию **10 000 токенов**, поиск и метки торговли.
- Отдельная страница адреса с прямой ссылкой, итогами покупок/продаж и всей доступной историей с пагинацией.
- Периоды 1 ч / 24 ч / 7 д / с заданной даты архива, фильтры, пагинация, CSV, автообновление, пауза экрана, мобильная версия.
- Светлая и тёмная темы: кнопка «Тема» рядом с LIVE. Выбор сохраняется в браузере; до первого ручного выбора используется системное оформление.
- SQLite WAL, защита от дублей, повторы ошибочных пакетов, восстановление курсоров, online-бэкап.

Этот раздел и описание двух сетей ниже относятся к прежнему APP_MODE=full. Не включайте его без необходимости: возобновятся прежние сборщики. Текущая панель ограничена WGNK на Ethereum.

## Windows + Docker

Нужен запущенный Docker Desktop. В PowerShell:

    Set-Location '.\gonka-live'
    docker compose up -d --build

Откройте [панель](http://127.0.0.1:8790).

    docker compose ps
    docker compose logs --tail 50

Остановить с сохранением истории:

    docker compose stop

Продолжить:

    docker compose start

Порт 8790 привязан только к 127.0.0.1: публикации в интернете или локальной сети нет. История — в именованном Docker-томе **gonka-live_gonka-data**. Не удаляйте том и не используйте команду down с флагом удаления томов, если хотите сохранить историю.

Сбор продолжается при закрытой вкладке, пока работают компьютер и Docker. После сна индексатор догоняет пропущенные блоки. Круглосуточная работа без компьютера потребует сервера.

## Без Docker

Python 3.12+:

    python -m venv .venv
    .\.venv\Scripts\python.exe -m pip install -r requirements.txt
    $env:APP_MODE='mints'
    .\.venv\Scripts\python.exe -m app

Остановка — Ctrl+C. Не запускайте Python и Docker одновременно на одном порту или несколько индексаторов с одной базой.

Python использует **data/gonka-flow.sqlite3**, Docker — отдельный том **/data**. Автоматической синхронизации между этими базами нет.

## Настройки и история прежнего режима full

В режиме mints используются APP_MODE, INDEXER_ENABLED, DATA_DIR и параметры ETH_RPC_URLS, ETH_ARCHIVE_RPC_URLS, ETH_RPC_INTERVAL, ETH_HISTORY_BATCH. Остальные параметры и июньская граница ниже не управляют индексом чеканки.

Сначала индексируются последние блоки, отдельно идёт обратная загрузка примерно суток Gonka до первого запуска. Для Ethereum сборщик держателей определяет первый блок WGNK и расширяет историю переводов/сделок до этого блока. Новые блоки накапливаются без автоматического удаления. «7 д» — фильтр, он не создаёт недостающую историю.

Внутри запрошенной глубины приоритетно загружаются несколько блоков границы текущей эпохи, чтобы раньше показать системные выплаты/разблокировки. Это отдельный небольшой диапазон, не полное покрытие промежутка.

В «Источниках и методе» показаны фактические диапазоны, число блоков, очередь и ошибки. Несколько диапазонов означают разрывы. Нулевой объём в неполном индексе не доказывает отсутствия активности.

Настройки задаются в файле **.env** рядом с compose.yaml по примеру **.env.example**. После изменения: docker compose up -d.

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| LOOKBACK_HOURS | 24 | Начальная приблизительная глубина |
| GONKA_START_HEIGHT | 0 | Явная нижняя граница Gonka; 0 — по глубине |
| ETH_START_HEIGHT | 0 | Явная нижняя граница Ethereum |
| HISTORY_FROM | пусто | ISO-дата с часовым поясом; нужны оба точных стартовых блока |
| POLL_SECONDS | 6 | Опрос Gonka при отсутствии отставания |
| NATIVE_BATCH | 6 | Блоков в атомарном пакете, максимум 16 |
| GONKA_RPC_URLS | https://rpc.gonka.gg | Полные корни RPC для блоков, через запятую |
| GONKA_URLS | 3 официальных узла | REST, active_participants, резервные RPC |
| ETH_RPC_URLS | MEV Blocker, PublicNode, dRPC | Ethereum RPC, через запятую |
| DATA_DIR | data; Docker: /data | Каталог SQLite |
| INDEXER_ENABLED | true | Отключение сборщиков для тестов/чтения |

При увеличении глубины нижняя граница расширяется, данные не стираются. Стартовые высоты задавайте меньше уже загруженных. Для genesis нужен архивный RPC. Публичный rpc.gonka.gg может хранить ограниченную историю; более ранние блоки потребуют официального архивного или собственного узла.

Публичные RPC имеют лимиты: официальный Gonka proxy по умолчанию задаёт 20 запросов в минуту с burst — [конфигурация](https://github.com/gonka-ai/gonka/blob/main/proxy/entrypoint.sh). Глубокая загрузка может занимать много часов и дольше. Есть ограничение частоты, cooldown после 429/503 и экспоненциальные повторы. Увеличение пакета не отменяет лимит провайдера.

### Архив с 7 июня 2026

В локальном .env настроено начало **07.06.2026 00:00 МСК** (06.06.2026 21:00 UTC, Unix 1780779600):

    HISTORY_FROM=2026-06-07T00:00:00+03:00
    GONKA_START_HEIGHT=4448701
    ETH_START_HEIGHT=25260902

Первый Gonka-блок имеет время 1780779600, предыдущий — 1780779595. Первый Ethereum-блок — 1780779611, предыдущий — 1780779599. При старте приложение повторно проверяет соседние блоки через RPC; неверное соответствие дате не принимается. Ethereum уже загружается от появления WGNK (#25088104), эта более ранняя история не удаляется.

Для другой даты сначала вычислите точные высоты (команда только читает RPC, не меняет БД):

    .\.venv\Scripts\python.exe -m app.history --from "2026-06-07T00:00:00+03:00"

Затем задайте все три переменные и перезапустите контейнер. Python без Docker читает переменные окружения, не подхватывает .env автоматически.

Кнопка «С 07.06» фильтрует сделки, переводы, мост и торговые метки по точной временной границе. На странице адреса такой же период есть в списке. API since (Unix-секунды) имеет приоритет над hours. Снимки балансов, цены и активных хостов остаются текущими/последними измеренными, не историческими на 7 июня.

Отдельная панель показывает покрытие запрошенного интервала каждой сети: сумма пересечений реально сохранённых диапазонов с [старт, текущий финальный блок], а не min/max дат. Несколько проверочных июньских блоков могут появиться раньше остального архива; они не закрывают разрыв. «Загружено» возможно только без пропусков. Новые блоки и глубокая история имеют отдельные статусы; задержка не называется ошибкой RPC.

Июньские block и block_results проверены на официальных node1/node2 05.09.2026. Публичный rpc.gonka.gg в этой проверке был обрезан до последних 100 000 блоков; приложение запоминает подтверждённую нижнюю границу и не повторяет заведомо невозможные запросы. Архивные резервные узлы распределяют запросы с прежним лимитом 3,2 с на узел. Это не гарантия доступности каждого промежуточного блока: при ошибке пакет и курсор не принимаются, ошибка отображается.

Для GNK это порядка 1,5 млн блоков и миллионы RPC-методов. Архив теперь использует стандартные JSON-RPC пакеты: по 5 блоков вместе с их block_results в одном HTTP-запросе. Полнота ID ответов, высоты, chain ID, число результатов транзакций и финальные хеши проверяются до записи всего пакета. Официальные node1/node2/node3 подтвердили пакетное чтение июньских, июльских и августовских блоков 05.09.2026; хеши совпали. Их лимит — 10 методов на пакет, поэтому более крупные задания делятся на пакеты не более 5 блоков. Между архивными HTTP-запросами к одному узлу остаётся минимум 4 с, расписание общее с обычными запросами. При 429/ошибке — пауза; курсор не продвигается. Если узел явно не поддерживает пакеты, остаётся обычный режим.

GONKA_ARCHIVE_RPC_URLS задаёт отдельные корни JSON-RPC полного архива. NATIVE_HISTORY_BATCH задаёт атомарное задание (1–24 блока, по умолчанию 5, максимум 5 блоков в одном HTTP-пакете); NATIVE_BATCH по-прежнему управляет только live. Если используется сторонний RPC, его тариф/лимиты могут считать отдельные методы внутри пакета. Увеличение размера не отменяет условия провайдера. Проверенная локальная граница даты переиспользуется при перезапуске, но не при изменении даты/начальных высот.

Docker должен оставаться запущенным. Срок зависит от фактической скорости и доступности всех старых блоков: одиночное чтение занимало бы недели, пакетный режим заметно сокращает количество HTTP-запросов. Для предсказуемого срока нужен архивный RPC с согласованной пропускной способностью либо проверенный совместимый экспорт; платные узлы автоматически не заказываются. Обычный state-sync snapshot ноды не заменяет полную историю событий. Это архив поддерживаемых ончейн-денежных событий, а не всех сообщений протокола, CEX/OTC или установленных личностей владельцев.

### Ethereum: live отдельно от архива

ETH_RPC_URLS обслуживает свежие блоки; ETH_ARCHIVE_RPC_URLS — исторические логи, блоки, receipts и исторический баланс WGNK. PublicNode оставлен для live, MEVBlocker — проверенный источник архива. На проверке 05.09.2026 PublicNode отвечал на архив 403 (нужен персональный токен), dRPC — 400 (нет доступного провайдера); поэтому они не являются архивными резервами по умолчанию. Публичный архив сейчас зависит от одного проверенного сервиса, SLA нет.

Очереди раздельные: не более 2 параллельных архивных задач и 4 live. Для одного endpoint расписание и rate-limit cooldown общие. ETH_RPC_INTERVAL=1 задаёт минимальный интервал в секундах; после 429 он увеличивается, Retry-After соблюдается, уже ожидающие задачи тоже выдерживают паузу. Недоступность исторических данных не отключает live того же RPC. Тела ошибок HTTP 400/403 разбираются, но сырые сообщения/URL с ключами не публикуются.

ETH_HISTORY_BATCH=1000 уменьшает стоимость повторения неуспешного пакета. Только ошибка размера getLogs делит диапазон; ошибки доступа/429 не создают дополнительные поддиапазоны. Проверки block hash, receipt, totalSupply и атомарных курсоров сохранены. В интерфейсе показывается время следующего повтора.

### Размер локального индекса

Замер 05.09.2026 после настройки: около 439 МБ основной SQLite, 8 МБ WAL и две резервные копии по 430/438 МБ — всего около 1,32 ГБ. Вторая согласованная копия создана перед включением пакетного режима, прежняя сохранена. Основной фиксированный объём — таблицы/индексы переписи примерно 1,15 млн держателей GNK, а не сами события. Предварительный порядок для завершённого индекса с июня — 1–3 ГБ; это экстраполяция, не верхняя граница (плотность исторических событий неизвестна). Практический резерв: 10 ГБ для индекса, 20 ГБ с копиями и временными файлами. Docker-образы и его виртуальный диск занимают место дополнительно.

## Как интерпретировать данные

### Сделки и адреса

Направление берётся из знака количества WGNK со стороны пула в Uniswap V3 Swap: положительное поступление в пул — продажа, отрицательное — покупка. Проверяются factory, token0, token1, fee и factory.getPool.

Адрес tx.from — **инициатор**, не автоматически человек-продавец. Для рейтинга сверяется направление суммарных ERC20-переводов WGNK инициатора в receipt. Инициатором может быть контракт-агрегатор. Оборот и покупки минус продажи не являются позицией, прибылью или чистым притоком капитала.

ERC20-перевод и Swap могут быть двумя строками ленты одной транзакции. DEX-оборот считает только Swap. Всю ленту нельзя суммировать как экономический оборот: финансирование вестинга, начисление и разблокировка тоже разные стадии.

Цена/ликвидность — внешний снимок DexScreener; сделка — лог Ethereum. Встречная сумма показана в USDT, не гарантированно в USD. Текущая цена не используется для переоценки исторических сделок.

### Мост

Официальный контракт WGNK и моста:

    0x972a7a92d92796a98801a8818bcf91f1648f2f68

GNK и WGNK имеют 9 знаков. GNK блокируется в bridge_escrow, WGNK выпускается 1:1. В обратном направлении WGNK сжигается, GNK освобождается. WGNK supply **не прибавляется** к native GNK supply.

«Нет второй стороны в индексе» не означает, что мост застрял. Возможны неполное покрытие, задержка RPC или неисполненный второй этап. BRIDGE_PENDING, чужой контракт и неоднозначные записи не считаются завершённым обратным переводом.

Связь двух адресов доказывает направление перевода, **не общее владение**. Она не доказывает, что позже были проданы именно эти монеты: актив взаимозаменяем.

### Хосты, выплаты, финальность

Хосты — active_participants текущей эпохи, не все когда-либо зарегистрированные аккаунты. Вес PoC не равен количеству GPU. Endpoint заявлен участником, не проверен как юридическое лицо. Произвольные URL хостов приложение не запрашивает.

ClaimRewards без денежных событий не считается выплатой. Выплата, награда в вестинг и разблокировка учитываются отдельно. Обычные переводы с вестингом не помечаются как майнинг. Получатель может отличаться от адреса хоста. Обрабатываются и системные события блока, и события успешных транзакций.

Gonka-блоки считаются финальными по CometBFT. Ethereum latest и finalized читаются отдельно: предварительный хвост атомарно пересканируется. Проверяются block hash лога и receipt; конфликт уже финального блока останавливает пакет. RPC-ошибки не заменяются нулевыми балансами.

Это индексатор доверенных публичных RPC, **не собственный проверяющий light client**, без SLA и гарантии полноты ответов провайдера.

### Не покрыто в версии 0.1

- CEX/OTC, частные расчёты, реальные личности владельцев.
- Нативные Cosmos/CosmWasm DEX как сделки, IBC и другие мосты.
- DEX вне поддерживаемых пулов. Новые найденные пулы отмечаются как неохваченные и требуют верификации и пересканирования.
- Бенефициарное владение: GNK в модулях вестинга/залога не разносится по конечным получателям; пулы WGNK не разложены по LP.
- Себестоимость майнинга, PnL, доходность оборудования, финансовые отчёты компаний.
- Автоматические утверждения о продажах командой/инсайдерами/майнерами без подтверждённых связей.

## Держатели и страницы адресов

Кнопка «Держатели» открывает GNK / WGNK. Начальный фильтр — **баланс ≥ 10 000** в единицах выбранного токена, не USD. Порог 0 показывает положительные балансы без отсечения. Нулевой адрес Ethereum исключён; нулевые балансы не считаются держателями. Пулы и системные модули показаны с отдельными ролями. GNK и обеспеченный им WGNK не суммируются как два разных капитала.

GNK: постраничная перепись через официальный cosmos.bank.denom_owners с фиксированным x-cosmos-block-height. На момент разработки API возвращал около 1,15 млн адресов, включая пылевые балансы. Страницы загружаются по 10 000 адресов с соблюдением лимитов RPC. Полнота подтверждается только после последней страницы, совпадения числа адресов и суммы с supply на том же блоке. Во время загрузки таблица неполная и не является полным топом сети.

Перепись GNK повторяется через 6 часов после завершения. Параллельно балансы адресов, замеченных в новых проиндексированных денежных событиях, перепроверяются через RPC. Блок и время измерения есть в строке. Остальные балансы остаются снимками, не гарантированными значениями на текущую секунду. Задержка native-индекса задерживает и эти обновления.

WGNK: держатели восстанавливаются из стандартных ERC-20 Transfer с первого блока существования официального контракта. Учитываются mint, burn и self-transfer; каждая пачка сверяется с историческим totalSupply. Балансы и курсор записываются атомарно. Финальный checkpoint проверяется на конфликт block hash. Пока курсор не догнал finalized, это явно помеченный промежуточный исторический список. История сделок индексируется отдельно и может отставать от готовности списка балансов.

Такая сверка не является криптографическим доказательством полноты ответа публичного RPC; нужен доверенный провайдер. Полная история и миллион адресов требуют места на диске и существенного первоначального трафика. Исторические eth_getCode/eth_call/eth_getLogs должны поддерживаться провайдером.

Метки «Покупает», «Продаёт», «Покупает и продаёт» основаны только на финальных Swap с attribution=initiator_net в выбранном периоде. Обычные переводы, мост, изменение LP и предварительные сделки не дают торговой метки. У GNK-адреса не появляется метка продавца из-за перевода через мост: адрес получателя Ethereum не доказывает общего владельца.

Нажатие на адрес открывает постоянный маршрут /#address/{address}. «Весь локальный индекс» (API hours=0) снимает временной фильтр и позволяет листать все сохранённые страницы, но не скрывает пробелы истории. Для WGNK по умолчанию открыт раздел сделок, для GNK — все операции. Кнопка «Проверить баланс» делает актуальный запрос через существующий поиск кошелька. Итоги торговли не являются позицией или PnL.

## Бэкап и объединение архивов

Не копируйте активную SQLite без WAL. Согласованный online backup:

    docker compose exec -T gonka-flow python -m app.backup /data/backup-2026-09-05.sqlite3
    docker cp gonka-live-gonka-flow-1:/data/backup-2026-09-05.sqlite3 ./backup-2026-09-05.sqlite3

Каждый раз выбирайте новое имя: существующий файл не перезаписывается. Храните копии отдельно от Docker-тома.

Объединение **доверенного архива Gonka Flow** с текущей историей без замены курсоров:

    docker cp ./backup-2026-09-05.sqlite3 gonka-live-gonka-flow-1:/tmp/import.sqlite3
    docker compose exec -T gonka-flow python -m app.import_history /tmp/import.sqlite3

Не импортируйте произвольные SQLite от третьих лиц. HTTP API загрузки/импорта нет. CLI-импорт появится на экране при очередном опросе.

## Позднее: Render

Подготовлен **render.yaml**, но **ничего не опубликовано и платные ресурсы не заказаны**.

1. Поместить содержимое gonka-live в корень отдельного Git-репозитория. Не публиковать .env, data, .venv, Telegram-экспорты и родительскую папку исследования.
2. Создать Render Blueprint из render.yaml.
3. Использовать один Docker web service с постоянным диском /data. Шаблон: платный план 1c-2g, диск 10 GB; цену и тариф подтвердить перед запуском.
4. Задать RPC и глубину. Для большого архива/публичной нагрузки предпочтительны выделенные RPC.
5. Проверить права пользователя контейнера на диск, оба сборщика, покрытие и финальность. При необходимости импортировать бэкап.

SQLite требует одного экземпляра и одного uvicorn worker. Не включать горизонтальный autoscaling. Free-сервис без постоянного диска не подходит для надёжного непрерывного индекса.

Перед публикацией: повторная проверка безопасности и зависимостей, бэкапы вне Render-диска, контроль роста БД, нагрузки и расходов RPC. Для большого трафика следующий этап — PostgreSQL/ClickHouse и отдельный индексатор.

Основание: [Render Blueprint](https://render.com/docs/blueprint-spec), [Persistent Disks](https://render.com/docs/disks).

## Разработка и проверки

FastAPI + asyncio/httpx → SQLite WAL → REST/SSE → HTML/CSS/JS без CDN.

    .\.venv\Scripts\python.exe -m unittest discover -s tests -v

Тестируются точные суммы, keccak, обе ориентации swap, пустые/ложные награды, разделение сообщений, LP, мост без двойного учёта, идемпотентность, покрытие с разрывами, реорганизация предварительных блоков, конфликт финального блока и API-валидация.

tools/ui-check.cjs — headless UI-тест с Playwright и Chrome. Для самостоятельного запуска установите Playwright отдельно как dev-зависимость. Рабочему приложению Node.js не нужен.

tools/theme-check.cjs проверяет темы, сохранение выбора, системную тему и отключённый localStorage. tools/holders-check.cjs проверяет порог 10k, страницы адресов, фильтры и мобильное отображение. tests/test_holders.py проверяет точные балансы, тегирование, атомарность и возобновление переписи.

tests/test_history.py проверяет точную дату, соседние блоки, разрывы покрытия, сохранение курсоров, отсечение pruned RPC и since-фильтр API. tools/history-check.cjs — выбор даты на всех экранах, профили, ошибки JavaScript и мобильная вёрстка.

tests/test_rpc.py — архивные пакеты GNK, переставленные/пропущенные ID, атомарность при ошибке, раздельные очереди Ethereum, Retry-After, wrong-chain, безопасные сообщения и деление только слишком больших диапазонов. tools/gonka-batch-check.py — ограниченная read-only проверка трёх старых блоков на каждом официальном узле, без изменения базы.

tools/probe.py и tools/inspect_sources.py — исследовательские пробы публичных источников. tools/smoke.py проверяет выбранные исторические mainnet-блоки и записывает их в локальную Python-БД; старые высоты могут стать недоступны без архивного RPC.
